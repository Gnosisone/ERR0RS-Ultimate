# Stress Test: Local LLM + RAG on Pi 5 CPU

**Date:** 2026-05-20
**Status:** Definitive finding — local LLM teach with full-fidelity RAG is **not viable** on Pi 5 CPU
**Logs:** `qwen_rag_small_2026-05-20-011527.log`, `llama3.2_3b_rag_small_2026-05-20-015429.log`

## What we tested

Could the Pi 5 cyberdeck run interactive RAG-augmented teach inference locally? Two models, same test:

- Pulled 1 teach card from ChromaDB (`kerberoasting active directory ticket extraction`)
- Built a 12,355-char prompt with ERR0RS soul + retrieved card + student question
- Streamed inference, capped at 300s wall clock, watched thermal closely

Test harness: `tools/stress_test_qwen_rag.py`

## What we found

| Model | Size | Peak Temp | Throttle | First Token | Result |
|---|---|---|---|---|---|
| err0rs-qwen (qwen2.5-coder:7b) | 4.8 GB | 66.1°C | None | Never | Hard timeout at 300s |
| llama3.2:3b | 3.0 GB | 59.0°C | None | Never | Hard timeout at 300s |

**Neither model produced a single output token in 5 minutes.**

## Why

The bottleneck is prompt evaluation throughput, not thermal limits and not model size. Pi 5's 4-core A76 @ 2.4 GHz handles llama.cpp inference at roughly:

- qwen-7B: ~12-15 tok/s prompt eval → ~3 min to chew through 3K tokens of input
- llama3.2:3b: ~25-30 tok/s prompt eval → ~2 min to chew through 3K tokens of input

A full RAG-injected prompt is dominated by the retrieved teach card (12K chars ≈ 3K tokens). Both models exceeded the wall clock before reaching the generation phase. The thermal kill switch (set at 80°C, last session hit 85.9°C) never fired — the Pi handled the workload cleanly.

**This is a throughput problem, not a thermal problem.**

## Paths forward (ranked by recommendation)

### A. Smaller retrieval chunks (recommended short-term)

Chunk each teach card into 2-3K char sections during ingestion. RAG retrieves only the relevant section, not the whole card. Prompt size drops from ~3K input tokens to ~750. Expected first-token latency on 3B model: 60-90s. Still not snappy, but interactive-feasible.

Implementation: ~1 session of work in `tools/ingest_teach_to_rag.py` plus a query-side chunking strategy.

### B. Hybrid runtime

Keep RAG retrieval local (CPU-cheap, ChromaDB on `all-MiniLM-L6-v2` is fast). Send the retrieved context + question to Claude/DeepSeek API for inference. Loses the strict "fully offline" promise for the teach feature, but ships today and uses cards we already paid Sonnet to generate.

Tradeoff: violates the charter's offline-first principle. Acceptable for a demo or "online teach mode" toggle; not acceptable as the default.

### C. Hailo-10H acceleration (long-term answer)

Wire a direct HailoRT inference backend. Already on the v3.9.0 roadmap. Blocked on the fact that Ollama doesn't natively use the Hailo NPU and the LLM models we want aren't in the .hef format the Hailo expects without conversion work. This is a 1-2 month project.

If solved, this becomes the definitive answer: fully offline, fast inference on a $400 cyberdeck.

### D. Try smaller models

Phi-3-mini (3.8B) and TinyLlama (1.1B) are worth a quick test, but the bottleneck is prompt-eval *throughput*, not parameter count. Probably won't fundamentally change the math. Worth running the same harness against them when there's time — `python3 tools/stress_test_qwen_rag.py --level small --model phi3:mini`.

## What does NOT help

- Lower `num_ctx` — doesn't help if the prompt itself is large; only helps cap how much context the *model* tracks during generation
- Lower `num_predict` — only affects generation length, not prompt eval
- Higher `temperature` — irrelevant
- Quantization — qwen2.5-coder:7b is already Q4_K_M; further quantization (Q3, Q2) costs quality without dramatically faster prompt eval
- Adding more cores — Pi 5 has 4. There aren't more.

## Decision

For v3.7+ runtime teach mode:

1. **Short-term:** implement Option A (chunked retrieval) — preserves offline-first, achievable in one session
2. **Demo/online toggle:** Option B (hybrid) — opt-in for users who want fastest possible teach and have API keys
3. **Long-term:** Option C (Hailo) — v3.9.0 roadmap target, real engineering project

The 67 fully-taught cards we shipped in v3.6.0 remain the right knowledge base. The bottleneck isn't the data — it's the inference substrate. We solve this by changing how we feed the data to the model, not by changing the data itself.
