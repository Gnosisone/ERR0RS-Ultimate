# v3.7.0 Plan — Local Teach Made Real

**Codename:** "Make the Pi Actually Teach"
**Predecessor:** v3.6.0 (Teach Knowledge Drop — 67 fully-taught tools + RAG)
**Successor planning:** v3.8.0 (Tier-2 BlackArch expansion), v3.9.0 (Hailo native)

## What v3.7.0 ships

v3.6.0 gave us the data. v3.7.0 wires the data into something a student on a Pi can actually use, offline, without burning $5 in API calls per study session. Three coordinated changes:

1. **Swap default local model to `gemma3:1b`** — the only model proven viable for Pi 5 RAG teach (see `docs/STRESS_TESTS/FINDINGS_2026-05-20.md`)
2. **Chunked RAG retrieval** — split 12K-char teach cards into 2-3K char sections so first-token latency drops from 145s to ~40-60s
3. **Online-teach toggle** — let users with `ANTHROPIC_API_KEY` / `DEEPSEEK_API_KEY` opt into cloud inference for snappier responses; default stays local

After v3.7.0 ships, the "Clippy on steroids" loop closes for the first time: student asks → RAG retrieves the right chunk → gemma3:1b explains in ERR0RS voice → student learns. All offline. All on a $400 cyberdeck.

---

## Why these three changes, in this order

The stress test on 2026-05-20 (qwen-7B fail, llama3.2:3b fail, gemma3:1b WIN) settled three previously-open questions:

| Question | Pre-v3.7 answer | Post-stress-test answer |
|---|---|---|
| Can Pi 5 CPU run RAG teach inference? | "Probably not" | YES, with gemma3:1b |
| What's the bottleneck? | "Thermal? Model size?" | Prompt-eval throughput per parameter |
| What model? | qwen2.5-coder:7b (broken default) | gemma3:1b (verified working) |

That last row is the single most important finding: **the current `llm_router.py` default points at a model that does not work on the Pi.** A new user installing ERR0RS today, with no API keys, would hit a 5-minute timeout on every teach request. v3.7.0 fixes that on day one.

## Phase 2 — Chunked RAG retrieval

**Scope:** 2 files (ingest + query helpers), one-time re-ingest of all 67 cards. Backward compatible — the existing `err0rs_teach_v1` collection stays usable; we add a new `err0rs_teach_v1_chunked` collection alongside.

**The problem we're solving:**
- Current RAG returns *whole teach cards* — average 12,158 chars each
- gemma3:1b on Pi 5 takes ~145s just to evaluate 12K chars of prompt
- A student-paced interactive session needs <60s to first token
- Solution: chunk each card into 2-3K char sections, retrieve the most relevant chunk only

**File 1:** `tools/ingest_teach_to_rag.py`

Add a chunked-ingest path that splits each card by its natural sections (`opsec_notes`, `sample_outputs`, `legal_notes`, `false_positives`, `mitre_attack`) plus the parent tool metadata as a header. Each chunk gets metadata `{tool: 'rubeus', section: 'opsec_notes', chunk_id: 0}` for filtering.

Pseudocode:
```python
def chunk_card(tool_key: str, card: dict) -> list[dict]:
    """Split a teach card into 2-3K char retrieval chunks.
    Each chunk carries enough header context to stand alone."""
    header = f"# {card['display_name']} — {card['category']} tool\n"
    header += f"{card['description'][:300]}\n\n"
    chunks = []
    for section in ('opsec_notes', 'sample_outputs', 'legal_notes',
                    'false_positives', 'mitre_attack'):
        body = render_section(card.get(section, []), section)
        if not body.strip():
            continue
        # Further split body if >2500 chars
        for sub_idx, piece in enumerate(split_by_chars(body, 2500)):
            chunks.append({
                "id": f"{tool_key}_{section}_{sub_idx}",
                "text": header + body_label(section) + piece,
                "metadata": {
                    "tool": tool_key,
                    "section": section,
                    "chunk_id": sub_idx,
                    "category": card.get('category'),
                }
            })
    return chunks
```

**File 2:** A new helper module `src/ai/rag_retrieval.py` (or extend `src/ai/rag_ingest_2026.py`) with a `retrieve_chunks(query: str, n: int = 2) -> list[str]` that queries the chunked collection and returns 1-2 chunks per query (vs the full card). Total prompt size targets:

- Before: 12K-char card + 500-char ERR0RS preamble + 200-char question = ~13K chars (~3K tokens)
- After: 2 × 2.5K-char chunks + preamble + question = ~6K chars (~1.5K tokens)

**Expected impact on first-token latency:**
- 12K-char prompt: 145s first token (measured)
- 6K-char prompt: ~70-90s first token (extrapolated from prompt-eval rate)
- 3K-char prompt (1 chunk): ~40-50s first token (interactive-feasible)

**Verification:**
```bash
python3 tools/stress_test_qwen_rag.py --level small --model gemma3:1b --chunked
# Expected: first_token < 90s, ideally < 60s
```

**Acceptance:** A teach request returns the first useful token within 90s on Pi 5, consistently, across 5 different queries.

## Phase 3 — Online-teach toggle

**Scope:** UI toggle + router config flag. No schema changes.

**The problem we're solving:**
- Local-default is great for privacy/cost, but a student doing focused study WANTS snappier responses
- They already have Claude/DeepSeek keys from running `tools/generate_teach.py` at build-time
- Currently `llm_router.py` falls back to remote providers only when local fails — should also support "user explicitly wants remote for this session"

**File:** `src/ai/llm_router.py` + UI wiring

Add a `route_mode` parameter to the router's primary entry point:
```python
def route(self, prompt: str, route_mode: str = "auto") -> LLMResponse:
    """
    route_mode:
      "auto"   — current behavior, local-first with remote fallback
      "local"  — local only, error if local unavailable
      "remote" — remote only (Claude > DeepSeek > GPT4), honors user keys
      "fast"   — alias for remote (UI-facing label)
    """
```

UI wires this through the `📚 TEACH ON/OFF` button by adding a second toggle: `🌐 FAST MODE` (online inference) alongside it. State persists per-session.

**Honest tradeoff to surface in the UI when FAST MODE is on:**
> ⚠️ FAST MODE sends your question to Claude/DeepSeek over the internet.
> Your local tool runs and findings stay on this device. Only the question
> + retrieved teach card gets sent. Toggle off to return to fully-local.

**Acceptance:**
1. With FAST MODE off: response comes from local gemma3:1b, first token in <90s
2. With FAST MODE on + Anthropic key set: response comes from Claude, first token in <5s
3. The UI clearly indicates which model is responding
4. Logs record which backend served each request (for audit/transparency)

## What this does NOT include (intentional cuts)

- **Fine-tuning gemma3:1b on ERR0RS soul** — Pi 5 cannot do LoRA training on a 1B model in reasonable time. Modelfile-based system-prompt baking (like err0rs-qwen has) is the right approach, deferred to v3.8.0 alongside the Tier-2 BlackArch expansion.
- **Streaming UI updates** — gemma3:1b's 6.83 tok/s is slow enough that streaming feels like watching paint dry. Better to render the full response when complete with a "thinking..." indicator. Streaming UI is a v3.8.0 enhancement.
- **Hailo backend** — v3.9.0 research project. Not blocking v3.7.0.
- **Multi-card RAG retrieval** — sticking with 1-2 chunks per query. Multi-card synthesis is harder to ground and slower to evaluate. Wait for runtime data before expanding.
- **GUI for the toggle** — text-based CLI toggle in v3.7.0; full GUI integration in v3.8.0.

## Open questions for the next session

1. **Modelfile for `err0rs-gemma`?** We baked the soul into `err0rs-qwen` already. Should we do the same for gemma3:1b — make an `err0rs-gemma` model with the ERR0RS soul embedded? Probably yes; ~5 min of work. Or stay with prompt injection at runtime for flexibility. Decide based on whether the gemma instruction-tuning is robust enough.
2. **Should `err0rs-qwen` stay installed at all?** Brief argument for: it's useful for code-heavy queries even if too slow for teach. Argument against: 4.7GB of disk for a use case we haven't validated. Probably remove from default install, keep as `install.sh --with-coder-model` opt-in.
3. **Should we test phi-3.5:mini before committing to gemma3:1b?** From research, phi-3.5 is "slower per token but more right per attempt." Worth a 7-min stress test if v3.7.0 isn't already shipping. Don't block on it though.
4. **Hailo timing reconsidered?** With gemma3:1b proving local teach is *possible* (just slow), does Hailo become less urgent or more? Probably less urgent — we have a workable baseline. Defer Hailo aggressively to v3.9.0.
